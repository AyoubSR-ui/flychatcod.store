PART 1 — SINGLE DOMINANT INTENT PER MESSAGE
--------------------------------------------------

Implement strict intent arbitration so each customer message can drive only ONE primary flow.

REQUIRED RULE
For every incoming customer message, decide one dominant intent only, such as:
- greeting
- product inquiry
- new order intent
- order confirmation
- cancellation intent
- thanks / closing
- human handoff

Once the dominant intent is selected:
- only that flow may execute
- all other flows must be skipped for this message

IMPORTANT
The backend must not allow:
- new-order response + cancellation response in the same turn
- cancellation response + product inquiry response in the same turn
- stale previous flow logic to emit a second message later for the same user input

Use a clear priority/arbitration layer before downstream handlers execute.

--------------------------------------------------
PART 2 — HARD RESET FROM CANCELLED FLOW TO NEW ORDER CYCLE
--------------------------------------------------

If a conversation is in or just completed cancellation flow, and the customer clearly starts a new order, the AI must reset into a fresh order cycle.

Examples of new order restart signals:
- راني حاب طلب من عندكم
- بغيـت نشري
- nheb ncommande
- can i make order
- je veux commander
- I want to order

REQUIRED BEHAVIOR
If the message is classified as clear new-order intent:
- clear stale cancellation choice state
- clear pending cancellation flow state
- do not run cancellation lookup for that message
- switch conversation flow state to new-order / collecting_order_details
- continue with product/order assistance only

This reset must be real backend state logic, not just prompt behavior.

--------------------------------------------------
PART 3 — PREVENT STALE / LATE BRANCH REPLIES
--------------------------------------------------

Fix any case where an old asynchronous branch can still emit a reply after the system already chose a different flow.

From the screenshots, this appears to be happening:
- one branch handles the new order correctly
- another stale branch still emits cancellation-related text

REQUIRED FIX
Introduce a guard so that for each customer message:
- only one AI reply can be emitted from the chosen branch
- stale branches must detect they lost arbitration and exit silently
- if one branch already committed a reply for the message, no second branch may emit another reply for the same trigger

Possible implementation:
- message-level processing token / operation lock
- chosenIntent stored for that message
- per-message reply-committed guard
Use the cleanest practical backend solution.
